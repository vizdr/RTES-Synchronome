# PREEMPT_RT on Raspberry Pi 4B

**Target hardware:** Raspberry Pi 4B  
**OS:** Debian GNU/Linux 13 (Trixie)  
**Kernel:** Linux 6.18.29+rpt-rpi-v8, aarch64

> **Trixie-specific notes** — Debian 13 differs from older Raspberry Pi OS (Bookworm/Bullseye)
> in several ways that affect this guide:
> - Boot files live exclusively in `/boot/firmware/`; `/boot/` is on the root filesystem
> - The `z50-raspi-firmware` dpkg hook auto-installs kernels into `/boot/firmware/` —
>   no manual file copies are needed after `apt-get install`
> - Swap is provided by **zram** (`systemd-zram-generator`), not a disk partition
> - CPU frequency is managed by **`linux-cpupower`** + `cpupower.service`, not `cpufrequtils`
> - **cgroup v2** (unified hierarchy) is the only cgroup interface — v1 commands do not work
> - `irqbalance` is **not installed** by default

---

## Part 1: Preemption Models and Their Effect on Deadlines

PREEMPT_RT is not just a config flag — it restructures most of the kernel's concurrency
infrastructure to make the kernel itself fully preemptible.

| Model | `CONFIG_` | Worst-case Latency | Effect on Deadlines |
|---|---|---|---|
| Server | `PREEMPT_NONE` | ~10–100 ms | Terrible; kernel sections are non-preemptible |
| Desktop | `PREEMPT_VOLUNTARY` | ~1–10 ms | Voluntary yield points only |
| Standard | `PREEMPT` | ~100 µs–1 ms | What ships with RPi OS by default |
| **Full RT** | **`PREEMPT_RT`** | **~10–100 µs** | **Kernel fully preemptible** |

Key mechanisms PREEMPT_RT enables:

- **Spinlocks → RT mutexes**: spinlocks become sleepable, so a high-priority thread waiting
  on one gets the CPU immediately when it is released
- **Priority inheritance**: prevents priority inversion — if a low-priority task holds a lock
  a high-priority waiter temporarily raises the holder's priority
- **Threaded IRQ handlers**: hardware interrupt handlers run as kernel threads with schedulable
  priority, so RT tasks can preempt them
- **High-resolution timers always enabled**: µs-level timer precision instead of `HZ`-tick
  granularity (250 Hz = 4 ms tick on RPi)

## Part 2: Verify Current Kernel Configuration

On Trixie, `/proc/config.gz` is not exposed by default. Read the config from `/boot/`:

```bash
uname -r
# 6.18.29+rpt-rpi-v8

grep -E "^CONFIG_(PREEMPT|HZ|HIGH_RES|NO_HZ)" /boot/config-$(uname -r)
```

Expected output on the stock RPi v8 kernel:

```
CONFIG_PREEMPT=y        # standard preemptible — NOT full RT
CONFIG_HZ_250=y         # 4 ms timer tick
CONFIG_HIGH_RES_TIMERS=y
CONFIG_NO_HZ_IDLE=y
```

The absence of `CONFIG_PREEMPT_RT=y` confirms you need to switch kernels.

After installing the RT kernel and rebooting, expose the running config via:

```bash
sudo modprobe configs          # loads configs.ko, exposes /proc/config.gz
zcat /proc/config.gz | grep CONFIG_PREEMPT_RT
# CONFIG_PREEMPT_RT=y
```

## Part 3: Install the PREEMPT_RT Kernel

The Raspberry Pi foundation ships an exact version match for 6.18.29 with PREEMPT_RT:
`linux-image-6.18.29+rpt-rpi-v8-rt`

### Step 1 — Install kernel and headers

```bash
sudo apt-get update
sudo apt-get install linux-image-rpi-v8-rt linux-headers-6.18.29+rpt-rpi-v8-rt
```

`linux-image-rpi-v8-rt` is a meta-package that tracks the latest RT kernel for your
architecture. The headers are needed if you build out-of-tree kernel modules (camera
drivers, CAN, etc.).

**What happens automatically on Trixie:** the `z50-raspi-firmware` dpkg post-install
hook runs immediately after `apt-get install` and:
1. Copies the kernel image to `/boot/firmware/kernel8_rt.img`
2. Copies updated DTBs and overlays to `/boot/firmware/`
3. Triggers `initramfs-tools` to generate `/boot/initrd.img-6.18.29+rpt-rpi-v8-rt`

You do **not** need to manually copy files.

### Step 2 — Verify the hook ran correctly

```bash
ls /boot/firmware/kernel8_rt.img      # kernel image placed by hook
ls /boot/vmlinuz-*-rpi-v8-rt          # source vmlinuz in /boot
ls /boot/initrd.img-*-rpi-v8-rt       # initramfs generated by initramfs-tools
```

### Step 3 — Select the RT kernel in config.txt

The RPi bootloader reads `/boot/firmware/config.txt`. The hook copies the kernel to
`kernel8_rt.img` but does **not** edit `config.txt` — do that manually:

```bash
sudo nano /boot/firmware/config.txt
```

Add `kernel=kernel8_rt.img` inside the `[all]` section. The `auto_initramfs=1` line
already present in Trixie's default config.txt tells the bootloader to automatically
load the matching initramfs — no `initramfs` directive is needed:

```ini
[all]
kernel=kernel8_rt.img          # added — selects the PREEMPT_RT kernel
auto_initramfs=1               # already present — auto-loads initrd for chosen kernel
dtoverlay=gpio-shutdown        # keep your existing overlays unchanged
```

### Step 4 — Reboot and verify

```bash
sudo reboot
```

After reboot:

```bash
uname -a
# Should show: ... 6.18.29+rpt-rpi-v8-rt ... SMP PREEMPT_RT ...

sudo modprobe configs
zcat /proc/config.gz | grep CONFIG_PREEMPT_RT
# Must show: CONFIG_PREEMPT_RT=y
```

## Part 4: Boot Command-Line Options (cmdline.txt)

Edit `/boot/firmware/cmdline.txt` — on Trixie this is the canonical location,
symlinked from `/boot/cmdline.txt`. This file is a **single line** — never insert newlines.

```
isolcpus=2,3 nohz_full=2,3 rcu_nocbs=2,3 threadirqs nosoftirq mitigations=off
```

| Parameter | What it does | Effect on deadlines |
|---|---|---|
| `isolcpus=2,3` | Removes CPUs 2–3 from the kernel's load-balancing pool. Tasks are only assigned to them via `taskset` / `pthread_setaffinity_np`. | Eliminates involuntary context switches from unrelated tasks — RT thread owns the full CPU |
| `nohz_full=2,3` | Adaptive-tick mode: when only one runnable task is on an isolated CPU, the 4 ms periodic tick is suppressed entirely. | Removes up to 4 ms of periodic interrupt jitter. Critical for sub-millisecond deadlines |
| `rcu_nocbs=2,3` | Offloads RCU (Read-Copy-Update) callbacks off the isolated CPUs onto housekeeping CPUs 0–1. | RCU callbacks can run for hundreds of µs; removing them from RT cores eliminates surprise latency spikes |
| `threadirqs` | Forces all threadable IRQ handlers to run as kernel threads (`irq/N-name`) rather than in hardirq context. | Allows `chrt`/`taskset` on IRQ handler threads, keeping them below your RT task's priority |
| `nosoftirq` | Moves softirq processing to `ksoftirqd` threads rather than running inline in the interrupted task's context. | Prevents your RT task from inheriting network/timer softirq work |
| `mitigations=off` | Disables Spectre/Meltdown mitigations (retpoline, IBRS, SSBD). | Measurable gain (~5–15% CPU) on RPi4. Trade security for determinism — **only in controlled/embedded environments** |

> CPUs 0–1 remain the "housekeeping" cores for the kernel, system services, IRQs, and RCU.  
> CPUs 2–3 become your RT-isolated cores.

## Part 5: IRQ Affinity — Keep Interrupts Off RT Cores

```bash
# View current IRQ-to-CPU assignments:
for i in /proc/irq/*/smp_affinity_list; do
    irq=$(echo $i | grep -o '[0-9]*')
    echo "IRQ $irq: $(cat $i)"
done

# Move all IRQs to housekeeping CPUs 0-1:
for irq in /proc/irq/*/smp_affinity_list; do
    echo 0-1 | sudo tee $irq > /dev/null
done
```

**On Trixie, `irqbalance` is not installed by default** — verify before acting:

```bash
systemctl status irqbalance 2>/dev/null || echo "irqbalance not installed"
# If it is installed, disable it:
sudo systemctl disable --now irqbalance
```

For your camera (V4L2 / USB IRQ), find its number and pin it:

```bash
grep -i "usb\|video\|cam" /proc/interrupts
echo 0-1 | sudo tee /proc/irq/<N>/smp_affinity_list
```

To make IRQ affinity persistent across reboots, create a systemd oneshot service:

```ini
# /etc/systemd/system/irq-affinity.service
[Unit]
Description=Set IRQ affinity to housekeeping CPUs
After=network.target

[Service]
Type=oneshot
ExecStart=/bin/bash -c 'for f in /proc/irq/*/smp_affinity_list; do echo 0-1 > $f; done'

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl enable irq-affinity
```

## Part 6: CPU Frequency — Disable Governor Transitions

The `ondemand` governor ramps frequency up when a task wakes, introducing 10–100 µs
of frequency-transition latency on each wakeup. On RPi4, all 4 cores share the same
clock domain, so the governor affects all cores simultaneously.

**Trixie ships `linux-cpupower` (already installed) and `cpupower.service`.**
Do not install `cpufrequtils` — it is not needed.

```bash
# Verify cpupower is present:
cpupower frequency-info | grep "current policy"
# current policy: governor "ondemand"  ← change this

# Apply performance governor immediately (takes effect now, lost on reboot):
sudo cpupower frequency-set -g performance

# Make persistent across reboots via cpupower.service:
sudo nano /etc/cpupower-service.conf
```

Uncomment and set the `GOVERNOR` line:

```ini
# /etc/cpupower-service.conf
GOVERNOR='performance'
```

Enable and start the service:

```bash
sudo systemctl enable --now cpupower.service

# Verify after reboot:
cpupower frequency-info | grep "current policy"
# current policy: governor "performance"
```

The RPi4 Cortex-A72 frequency steps range from 600 MHz to 1800 MHz. With `performance`,
the CPU runs at 1800 MHz always — your RT thread wakes and gets full clock speed
immediately, with zero ramp-up delay.

## Part 7: Disable Swap

A page fault against a swapped-out page triggers I/O — potentially milliseconds of
latency. The `mlockall(MCL_CURRENT | MCL_FUTURE)` call in your RT application locks
its own pages into RAM, but kernel threads and other processes can still trigger swap
pressure that affects memory allocator behaviour on your RT core.

**Trixie uses zram swap** (`systemd-zram-generator`), not a disk partition or
`dphys-swapfile`. The swap device is `/dev/zram0` — a compressed in-RAM block device.
Do **not** edit `/etc/fstab` (there is no swap entry there).

```bash
# Confirm the zram swap is active:
swapon --show
# NAME       TYPE      SIZE USED PRIO
# /dev/zram0 partition   2G   0B  100

# Option A — disable zram swap permanently (recommended for dedicated RT systems):
sudo nano /etc/systemd/zram-generator.conf
```

Remove or comment out the `[zram0]` section entirely:

```ini
# /etc/systemd/zram-generator.conf
# [zram0]     ← comment out or delete this section to disable zram swap
```

```bash
sudo systemctl mask systemd-zram-setup@zram0.service
sudo swapoff /dev/zram0
# Verify:
swapon --show    # should produce no output

# Option B — keep zram but prevent RT pages from being swapped out:
# Use mlockall() in your application (see Part 8) — this is sufficient
# if you accept zram remaining active for non-RT processes.
```

> **Why zram is less dangerous than disk swap:** zram decompresses pages in RAM —
> no disk I/O. However, the compression/decompression itself consumes CPU cycles
> and can cause cache pollution. For strict RT, Option A (full disable) is cleaner.

## Part 8: RT Thread Scheduling in Application Code

### Scheduling policies

| Policy | API | Priority | How it works | Use when |
|---|---|---|---|---|
| `SCHED_OTHER` | default | nice -20..19 | CFS, fair sharing | Non-RT tasks |
| `SCHED_FIFO` | `sched_setscheduler` | 1–99 | Runs until it blocks or yields; higher priority always wins | Periodic tasks with known period |
| `SCHED_RR` | `sched_setscheduler` | 1–99 | FIFO with time quantum; same-priority tasks round-robin | Multiple equal-priority RT tasks |
| `SCHED_DEADLINE` | `sched_setattr` | EDF | Earliest-Deadline-First; kernel enforces `runtime` within `period` | When exact timing parameters are known |

### SCHED_FIFO setup

```c
#include <sched.h>
#include <sys/mman.h>

void rt_init(int priority)
{
    /* Lock all current and future memory pages — prevents page faults
     * (page fault = potential disk I/O = ms-level delay) during RT execution. */
    mlockall(MCL_CURRENT | MCL_FUTURE);

    struct sched_param param = { .sched_priority = priority };
    /* Priority 99 = highest RT; use 80-90 for your task,
     * leave 91-99 for watchdog / critical system threads. */
    if (sched_setscheduler(0, SCHED_FIFO, &param) < 0)
        perror("sched_setscheduler");
}
```

### SCHED_DEADLINE setup (most precise for periodic tasks)

The kernel enforces the timing contract: if the task overruns `sched_runtime`, it
is throttled (SIGXCPU) — protecting all other tasks from a misbehaving RT thread.

```c
#include <stdint.h>
#include <sys/syscall.h>
#include <unistd.h>

struct sched_attr {
    uint32_t size;
    uint32_t sched_policy;
    uint64_t sched_flags;
    int32_t  sched_nice;
    uint32_t sched_priority;
    uint64_t sched_runtime;   /* max CPU time per period (nanoseconds) */
    uint64_t sched_deadline;  /* relative deadline from period start (nanoseconds) */
    uint64_t sched_period;    /* period length (nanoseconds) */
};

void set_deadline_task(uint64_t runtime_ns, uint64_t deadline_ns, uint64_t period_ns)
{
    struct sched_attr attr = {
        .size           = sizeof(attr),
        .sched_policy   = SCHED_DEADLINE,
        .sched_runtime  = runtime_ns,    /* e.g. 2 ms = 2000000 */
        .sched_deadline = deadline_ns,   /* e.g. 8 ms = 8000000 */
        .sched_period   = period_ns,     /* e.g. 10 ms = 10000000 */
    };
    if (syscall(SYS_sched_setattr, 0, &attr, 0) < 0)
        perror("sched_setattr");
}
```

### Pin RT thread to an isolated core

```c
#include <pthread.h>

void pin_to_core(int core)
{
    cpu_set_t cpuset;
    CPU_ZERO(&cpuset);
    CPU_SET(core, &cpuset);
    pthread_setaffinity_np(pthread_self(), sizeof(cpuset), &cpuset);
}
/* Call inside the RT thread with core = 2 or 3 */
```

### Priority assignment guidelines for a camera pipeline

```
Priority 99  — hardware watchdog (if any)
Priority 85  — camera frame capture thread   ← your SCHED_FIFO RT thread
Priority 70  — image processing thread
Priority 50  — output / streaming thread
Priority  1  — SCHED_FIFO baseline (still above all SCHED_OTHER tasks)
              — normal OS services use SCHED_OTHER (effectively priority 0 in RT terms)
```

## Part 10: What PREEMPT_RT Actually Changes Internally

### 10.1 Timer Subsystem

**SMP PREEMPT — callback runs in interrupt context:**

```
Hardware timer IRQ
  └─► hardirq handler (non-preemptible, IRQs disabled)
        └─► raises HRTIMER_SOFTIRQ / TIMER_SOFTIRQ
              └─► softirq runs (still in interrupt context, non-preemptible)
                    └─► expires timer callbacks ← your RT task cannot preempt this
```

**PREEMPT_RT — callback runs in a schedulable thread:**

```
Hardware timer IRQ
  └─► minimal top-half: ACK hardware only (~microseconds)
        └─► wakes ktimers / ksoftirqd kernel thread
              └─► thread is schedulable — your RT task can preempt it
                    └─► expires timer callbacks
```

`hrtimer` callbacks are now split:
- `HRTIMER_MODE_HARD` — true hardirq context, used only for the clock infrastructure itself
- `HRTIMER_MODE_SOFT` (default) — runs in `ksoftirqd` thread, preemptible

`HRTIMER_SOFTIRQ` as a softirq type is **eliminated** — hrtimers go through the `ktimers`
thread path entirely.

---

### 10.2 Spinlocks → RT Mutexes (the central change)

| Lock type | SMP PREEMPT | PREEMPT_RT |
|---|---|---|
| `spinlock_t` | true spin, disables preemption | sleeping `rt_mutex`, fully preemptible |
| `rwlock_t` | true spin, disables preemption | sleeping `rt_rwlock` with PI |
| `mutex_t` | sleeping lock, **no** priority inheritance | `rt_mutex` **with PI** |
| `rw_semaphore` | sleeping lock, no PI | `rt_rwsem` with PI |
| `raw_spinlock_t` | true spin | **unchanged** — used only in ~20 truly atomic kernel paths |

**Priority Inheritance (PI) — why it matters for deadlines:**

```
Without PI (SMP PREEMPT):         With PI (PREEMPT_RT):

LP holds spinlock                  LP holds RT mutex
HP blocks waiting (spinning)       HP blocks waiting
MP preempts LP  ← BAD              LP inherits HP priority
HP waits for both MP and LP        LP runs at HP priority, finishes quickly
Deadline missed                    HP unblocks and meets deadline
```

---

### 10.3 IRQ / Interrupt Handling

**SMP PREEMPT — full handler in hardirq context:**

```
HW interrupt fires
  └─► CPU enters hardirq vector (local IRQs disabled)
        └─► runs full IRQ handler function (can take ms for network/USB)
              └─► handler returns, local IRQs re-enabled
                    └─► softirqs run (still non-preemptible)
```

**PREEMPT_RT — handler split into top-half + schedulable thread:**

```
HW interrupt fires
  └─► CPU enters hardirq vector
        └─► top-half: ACK device, store minimal data, wake irq_thread (~<5 µs)
              └─► returns immediately, IRQs re-enabled
                    └─► irq_thread kthread wakes (SCHED_FIFO priority 50 default)
                          └─► fully preemptible by any higher-priority RT task
```

Adjust IRQ thread priorities:

```bash
# List IRQ threads:
ps -eo pid,policy,rtprio,comm | grep "^.*irq"

# Lower a specific IRQ thread so your RT task preempts it:
chrt -f -p 30 $(pgrep "irq/47-eth0")
```

**`local_irq_disable()` behavior change:**

In most non-critical code paths, `local_irq_disable()` is replaced by `local_lock()` —
a per-CPU sleeping lock. Hardware IRQs remain **physically enabled** on the CPU; only the
logical critical section is protected. Only `raw_local_irq_disable()` still disables
hardware IRQ delivery.

---

### 10.4 Softirqs

**SMP PREEMPT — 10 softirq types, all in interrupt context:**

```
TIMER_SOFTIRQ    — expired timer callbacks
NET_TX / NET_RX  — network packet processing
BLOCK            — block I/O completion
TASKLET          — deferred driver work
SCHED            — load balancing
RCU              — RCU callbacks
HRTIMER          — hrtimer callbacks
```

All run non-preemptibly. A burst of network receive packets can loop for milliseconds
while your RT task waits.

**PREEMPT_RT — every softirq runs in a schedulable `ksoftirqd/N` thread:**

```bash
ps -eo pid,policy,rtprio,comm | grep softirq
# ksoftirqd/0, /1, /2, /3 — SCHED_OTHER by default
# Lower their priority so your RT task always beats them:
chrt -f -p 10 $(pgrep "ksoftirqd/2")
```

`HRTIMER_SOFTIRQ` is eliminated — hrtimers run through the `ktimers` thread.
Tasklets also run in thread context (`tasklet_work`).

---

### 10.5 RCU (Read-Copy-Update)

RCU is the kernel's lock-free read synchronization used throughout networking, VFS,
scheduler, and device driver subsystems.

**SMP PREEMPT:**

```c
rcu_read_lock();    /* disables preemption — RCU reader cannot be preempted */
/* read shared data */
rcu_read_unlock();  /* re-enables preemption */
```

**PREEMPT_RT (Preemptible RCU):**

```c
rcu_read_lock();    /* increments a per-task counter — does NOT disable preemption */
/* read shared data — task CAN be preempted mid-section */
rcu_read_unlock();  /* decrements counter */
```

Consequences:
- Grace periods can be longer (a preempted reader prolongs the period)
- RCU callbacks run in `rcuc/N` and `rcuo/N` kthreads instead of softirq
- `rcu_nocbs=2,3` in `cmdline.txt` offloads all callback processing off your RT cores

---

### 10.6 Memory Allocation

The SLUB allocator uses `spinlock_t` internally in SMP PREEMPT — a spinlock held during
allocation disables preemption for the entire allocation duration.

In PREEMPT_RT, SLUB uses `local_lock_t` (a per-CPU sleeping lock) instead, so:
- Allocations no longer cause preemption-disable latency spikes
- Many paths that previously required `GFP_ATOMIC` can now use `GFP_KERNEL`
- `GFP_ATOMIC` remains only for the narrow true-hardirq top-half paths

---

### 10.7 Per-CPU Variables and `local_lock`

**SMP PREEMPT:**

```c
cpu = get_cpu();           /* preempt_disable() */
data = per_cpu(my_data, cpu);
put_cpu();                 /* preempt_enable() */
```

**PREEMPT_RT:**

```c
local_lock(&my_local_lock);         /* per-CPU sleeping mutex */
data = this_cpu_ptr(&my_data);
local_unlock(&my_local_lock);       /* allows sleeping while "owning" the per-CPU section */
```

This pattern is pervasive across the kernel — networking, memory management, and the
scheduler itself all use `local_lock` in PREEMPT_RT builds.

---

### 10.8 `printk` / Console Output

**SMP PREEMPT:** `printk()` acquires a spinlock and writes directly to the console UART.
At 115200 baud, writing 100 bytes takes ~8.7 ms of spinlock-held, preemption-disabled
time — visible as RT latency spikes whenever the kernel logs anything.

**PREEMPT_RT:**
1. `printk()` writes to a **lockless ring buffer** (returns in microseconds)
2. A dedicated `printk` kthread flushes the ring buffer to the console asynchronously

Your RT task is never delayed by UART speed. Tradeoff: log messages appear slightly
after the event — use `ftrace` for precise RT debugging rather than `printk`.

---

### 10.9 `in_interrupt()` Context Semantics

**SMP PREEMPT:**

```c
in_interrupt()   /* true if: hardirq OR softirq OR spinlock held (preempt_count > 0) */
irqs_disabled()  /* true if hardware IRQs disabled on this CPU */
```

**PREEMPT_RT:**

```c
in_interrupt()   /* much narrower: only true in hardirq top-half */
in_softirq()     /* false in ksoftirqd thread context */
irqs_disabled()  /* often false even "inside" former IRQ-disabled sections */
```

PREEMPT_RT adds `might_sleep()` assertions to many more kernel paths. Any code that
calls a sleeping lock in a context that should not sleep triggers a warning — this
surfaces latent bugs during development that were silently incorrect before.

---

### 10.10 Complete Comparison Table

| Subsystem | SMP PREEMPT | PREEMPT_RT | Deadline impact |
|---|---|---|---|
| `spinlock_t` | spin + preempt disable | sleeping RT mutex + PI | Eliminates unbounded priority inversion |
| Hardirq handler | full handler, IRQs off | ACK only (~µs), rest in kthread | RT task can preempt IRQ processing |
| Softirqs | interrupt context, non-preemptible | `ksoftirqd` kthreads, schedulable | Network/IO can no longer block RT task |
| `hrtimer` callbacks | hardirq or softirq context | `ktimers` thread, schedulable | Timer callbacks preemptible by RT task |
| `rcu_read_lock()` | disables preemption | counter only, fully preemptible | No preemption disable in RCU sections |
| RCU callbacks | in softirq | `rcuc`/`rcuo` kthreads | Offload off RT cores with `rcu_nocbs=` |
| `local_irq_disable()` | disables HW IRQs | `local_lock()` per-CPU mutex | HW IRQs remain enabled in most paths |
| `printk()` | UART write under spinlock (ms!) | async kthread, lockless ring buffer | No console latency spikes |
| `mutex_lock()` | sleeping, no PI | RT mutex with PI | Priority inheritance on all mutex paths |
| SLUB allocator | spinlock-protected | `local_lock`-protected | Allocations don't cause preempt spikes |
| `might_sleep()` | sparse | pervasive | Surfaces sleeping-in-atomic bugs early |

```
[ ] Move all IRQs to CPUs 0-1 via /proc/irq/*/smp_affinity_list
[ ] Create /etc/systemd/system/irq-affinity.service for persistence

CPU frequency (Trixie — uses linux-cpupower, not cpufrequtils):
[ ] Edit /etc/cpupower-service.conf: set GOVERNOR='performance'
[ ] sudo systemctl enable --now cpupower.service
[ ] Verify: cpupower frequency-info | grep "current policy"

Swap (Trixie — uses zram, not fstab):
[ ] Edit /etc/systemd/zram-generator.conf: comment out [zram0] section
[ ] sudo systemctl mask systemd-zram-setup@zram0.service
[ ] sudo swapoff /dev/zram0
[ ] Verify: swapon --show (should be empty)

AMP CPU partitioning — cgroup v2 (Trixie):
[ ] echo "+cpuset" | sudo tee /sys/fs/cgroup/cgroup.subtree_control
[ ] Create /etc/systemd/system/rt-work.slice with AllowedCPUs=2-3
[ ] Create /etc/systemd/system/system.slice.d/cpus.conf with AllowedCPUs=0-1
[ ] sudo systemctl daemon-reload

Application code:
[ ] mlockall(MCL_CURRENT | MCL_FUTURE) at startup
[ ] SCHED_FIFO (sched_setscheduler) or SCHED_DEADLINE (sched_setattr)
[ ] pthread_setaffinity_np() to pin RT thread to CPU 2 or 3

Validation:
[ ] Lower ksoftirqd/2, ksoftirqd/3 priorities below your RT task
[ ] Lower IRQ thread priorities (chrt -f -p 30) for USB/camera IRQs
[ ] sudo cyclictest --mlockall --priority=80 --affinity=2 --loops=100000
[ ] Repeat under stress-ng load
```

**Biggest gains in order:** (1) PREEMPT_RT kernel, (2) `nohz_full` on isolated cores,
(3) `mlockall()` in your application, (4) performance CPU governor.
IRQ affinity and `rcu_nocbs` remove the remaining tail latency.

### 12.3 Preemption Model

**Path:** `General setup` → `Preemption Model`

```
( ) No Forced Preemption (Server)
( ) Voluntary Kernel Preemption (Desktop)
( ) Preemptible Kernel (Low-Latency Desktop)
(X) Fully Preemptible Kernel (Real-Time)        ← select this
```

| Option | `CONFIG_` | Effect on deadlines |
|---|---|---|
| No Forced Preemption | `PREEMPT_NONE` | Kernel sections run to completion; worst-case ms latency |
| Voluntary Preemption | `PREEMPT_VOLUNTARY` | Code calls `cond_resched()` at safe points; ~1–10 ms |
| Preemptible Kernel | `PREEMPT` | Stock RPi kernel; preemption at most kernel boundaries; ~100 µs–1 ms |
| **Fully Preemptible** | **`PREEMPT_RT`** | Spinlocks → RT mutexes, IRQs threaded; **~10–100 µs** |

Selecting `PREEMPT_RT` auto-enables: `PREEMPT_RCU`, `IRQ_FORCED_THREADING`,
`PREEMPT_COUNT`, and changes `spinlock_t` to sleeping locks throughout the build.

### 12.4 Timer Subsystem

**Path:** `General setup` → `Timers subsystem`

#### Timer tick handling

```
( ) Periodic timer ticks (constant rate, no dynticks)   CONFIG_HZ_PERIODIC
( ) Idle dynticks system (tickless idle)                CONFIG_NO_HZ_IDLE   ← stock RPi
(X) Full dynticks system (tickless)                     CONFIG_NO_HZ_FULL   ← enable this
```

| Option | Effect |
|---|---|
| `HZ_PERIODIC` | Fixed tick always fires — simplest, highest jitter on idle CPUs |
| `NO_HZ_IDLE` | Tick suppressed when CPU is idle; restarts on any wakeup |
| **`NO_HZ_FULL`** | **Tick also suppressed when exactly one task runs on a CPU** — removes 4 ms periodic interrupt jitter from isolated RT cores entirely. Requires `nohz_full=2,3` in `cmdline.txt` to activate per-CPU |

After selecting `NO_HZ_FULL`, two sub-options appear:

- **`Full dynticks system - keep RCU in full dynticks mode`** (`CONFIG_RCU_NOCB_CPU`) —
  offloads RCU callbacks off `nohz_full` CPUs. **Enable this.** Without it, RCU callbacks
  still fire on your isolated cores and break tick suppression.

- **`Housekeeping CPU for full dynticks`** — lets you bake in a static housekeeping CPU
  mask at compile time; usually leave blank and use `nohz_full=` boot parameter instead.

#### High Resolution Timers

**Path:** `General setup` → `Timers subsystem` → `High Resolution Timer Support`

```
[*] High Resolution Timer Support       CONFIG_HIGH_RES_TIMERS
```

Always enable. Without it, all timers have ±4 ms resolution (one `HZ=250` tick).
With it, `hrtimer` gives µs-level precision, and `clock_nanosleep(CLOCK_MONOTONIC, ...)`
wakes within ~10–50 µs of the requested time on PREEMPT_RT.

#### Timer Frequency (HZ)

**Path:** `Kernel Features` → `Timer frequency` (ARM64 sub-menu)

```
( ) 100 Hz    CONFIG_HZ_100    — 10 ms tick, lowest overhead, worst resolution
( ) 250 Hz    CONFIG_HZ_250    — 4 ms tick  (stock RPi)
( ) 300 Hz    CONFIG_HZ_300    — 3.3 ms tick
(X) 1000 Hz   CONFIG_HZ_1000   — 1 ms tick
```

| HZ | Tick period | Use case |
|---|---|---|
| 100 | 10 ms | Server, batch workloads |
| 250 | 4 ms | Desktop (RPi default) |
| 1000 | 1 ms | RT with `NO_HZ_FULL` disabled; also tightens jitter for `NO_HZ_IDLE` CPUs |

With `NO_HZ_FULL` enabled and `nohz_full=2,3` in the boot command, HZ only matters
for the housekeeping CPUs (0–1) — the isolated CPUs run tick-free regardless.
Still, set `HZ_1000` on housekeeping cores to reduce scheduling granularity on them.

### 12.5 RCU Subsystem

**Path:** `General setup` → `RCU Subsystem`

| Option | `CONFIG_` | Default (6.18 RPi) | Recommendation |
|---|---|---|---|
| Offload RCU callbacks from boot-selected CPUs | `RCU_NOCB_CPU` | not set | **Enable** |
| Enable RCU priority boosting | `RCU_BOOST` | not set | Enable |
| RCU boost delay (ms) | `RCU_BOOST_DELAY` | — | 500 ms (default) |

**`RCU_NOCB_CPU`** — when enabled, the `rcu_nocbs=2,3` boot parameter becomes available.
It moves all RCU grace-period callbacks off CPUs 2–3 to dedicated `rcuo/N` kthreads on
the housekeeping CPUs. Without this, RCU callbacks can fire at any time on your RT core
and cause latency spikes of 100–500 µs.

**`RCU_BOOST`** — if an RCU grace period is delayed because a low-priority task holds
an RCU read-side critical section, this option boosts that task's priority to
`RCU_BOOST_PRIO` (default 1) so it exits faster. Reduces worst-case grace-period latency.

**`RCU_BOOST_DELAY`** — milliseconds before priority boost kicks in (default 500 ms).
Lower this (e.g. 100 ms) for tighter RT systems.

### 12.6 CPU Isolation (AMP Core Partitioning)

**Path:** `General setup` → `CPU isolation`  
or search `/` → `CPU_ISOLATION`

```
[*] CPU isolation       CONFIG_CPU_ISOLATION
```

This enables the `isolcpus=` kernel parameter infrastructure. Without it, the parameter
is silently ignored. The stock 6.18 RPi config already has this enabled.

The `isolcpus=` parameter accepts isolation domain flags (kernel 5.x+):

```
isolcpus=domain:2,3          # remove from scheduler domain (load balancing)
isolcpus=nohz:2,3            # suppress tick (older alias for nohz_full)
isolcpus=managed_irq:2,3     # only allow explicitly-affined managed IRQs
isolcpus=domain,managed_irq:2,3   # combine flags (recommended)
```

**`domain`** — removes CPUs from `sched_domain` hierarchy so the load balancer never
migrates tasks onto them. A task running on CPU 2 stays on CPU 2 until it blocks or
explicitly migrates itself.

**`managed_irq`** — blocks affinity-unset (non-managed) IRQs from landing on isolated
CPUs. Combined with `domain`, this is the cleanest AMP isolation available without
running a hypervisor.

### 12.7 IRQ Threading

**Path:** `General setup` → `IRQ subsystem` or search `/` → `IRQ_FORCED_THREADING`

```
[*] Force irq threading        CONFIG_IRQ_FORCED_THREADING
```

The stock 6.18 RPi kernel already enables this. With `PREEMPT_RT` selected, it is
automatically forced on and cannot be disabled — all non-`IRQF_NO_THREAD` handlers
become kernel threads.

Effect: each IRQ handler (`irq/N-name`) becomes a schedulable `SCHED_FIFO` kthread
at priority 50. You can lower the priority of IRQs that compete with your RT task:

```bash
# After boot — lower USB IRQ thread below your RT task (priority 80):
chrt -f -p 30 $(pgrep "irq/.*usb")
```

### 12.8 CPU Frequency Scaling

**Path:** `CPU Power Management` → `CPU Frequency scaling`

```
[*] CPU Frequency scaling                           CONFIG_CPU_FREQ
    Default CPUFreq governor (ondemand)  --->
        (X) performance                             CONFIG_CPU_FREQ_DEFAULT_GOV_PERFORMANCE
    [*] 'performance' cpufreq governor              CONFIG_CPU_FREQ_GOV_PERFORMANCE
    [*] 'schedutil' cpufreq governor                CONFIG_CPU_FREQ_GOV_SCHEDUTIL
```

| Governor | Behavior | RT latency impact |
|---|---|---|
| `ondemand` | Ramps frequency on load detection; slow ramp | 10–100 µs wakeup latency from frequency transition |
| `powersave` | Minimum frequency always | Consistent but slow — bad for RT throughput |
| `schedutil` | Frequency follows CFS utilization signals | Better than ondemand but still not deterministic |
| **`performance`** | **Maximum frequency always** | **Zero frequency-transition latency — recommended for RT** |

Set `performance` as the **default governor** at compile time so it is active before
userspace starts.

### 12.9 Control Groups and CPUSET (AMP Partitioning)

**Path:** `General setup` → `Control Group support`

```
[*] Control Group support                           CONFIG_CGROUPS
    [*] Cpuset controller                           CONFIG_CPUSETS
    [*] Include legacy /proc/<pid>/cpuset file      CONFIG_PROC_PID_CPUSET
    [*] Group CPU scheduler                         CONFIG_CGROUP_SCHED
    [ ] RT bandwidth control                        CONFIG_RT_GROUP_SCHED  (see below)
```

**`CPUSETS`** — enables the cgroup `cpuset` controller. This is the kernel mechanism
for **static AMP partitioning**: you create two cgroups, assign CPUs 0–1 to the
system cgroup and CPUs 2–3 to the RT cgroup, then move processes between them.

**Trixie uses cgroup v2 exclusively** (unified hierarchy). The v1 commands
(`/sys/fs/cgroup/cpuset/…`) do not exist. Use the v2 interface:

```bash
# Step 1 — enable the cpuset controller at the root level:
echo "+cpuset" | sudo tee /sys/fs/cgroup/cgroup.subtree_control

# Step 2 — create the RT partition cgroup:
sudo mkdir /sys/fs/cgroup/rt_partition

# Step 3 — assign isolated CPUs and memory node:
echo "2-3" | sudo tee /sys/fs/cgroup/rt_partition/cpuset.cpus
echo "0"   | sudo tee /sys/fs/cgroup/rt_partition/cpuset.mems

# Step 4 — move your RT process into the partition:
echo $RT_PID | sudo tee /sys/fs/cgroup/rt_partition/cgroup.procs

# Verify:
cat /sys/fs/cgroup/rt_partition/cpuset.cpus    # should show: 2-3
cat /sys/fs/cgroup/cpuset.cpus.isolated        # shows isolated CPUs (set by isolcpus=)
```

**Preferred Trixie method — systemd slice with `AllowedCPUs`:**

Create a dedicated slice for RT work. systemd translates `AllowedCPUs=` directly
to `cpuset.cpus` in the cgroup v2 interface:

```ini
# /etc/systemd/system/rt-work.slice
[Slice]
AllowedCPUs=2-3
```

```bash
sudo systemctl daemon-reload

# Launch your RT service inside the slice:
# In the service unit file:
#   [Service]
#   Slice=rt-work.slice
#   CPUSchedulingPolicy=fifo
#   CPUSchedulingPriority=80

# Or ad-hoc via systemd-run:
sudo systemd-run --slice=rt-work.slice --property=CPUSchedulingPolicy=fifo \
    --property=CPUSchedulingPriority=80 /path/to/your/rt_app
```

**Restrict the system slice to housekeeping CPUs:**

```ini
# /etc/systemd/system/system.slice.d/cpus.conf
[Slice]
AllowedCPUs=0-1
```

```bash
sudo systemctl daemon-reload
# All system services are now confined to CPUs 0-1
```

**`RT_GROUP_SCHED`** — enables per-cgroup RT bandwidth throttling. When enabled, the
kernel enforces that all SCHED_FIFO/RR tasks in a cgroup consume at most
`/proc/sys/kernel/sched_rt_runtime_us` microseconds per
`sched_rt_period_us` period (default: 950 ms out of every 1000 ms).

> **Warning:** `RT_GROUP_SCHED` is **incompatible with `SCHED_DEADLINE`** — enabling
> it prevents any task from using `SCHED_DEADLINE` unless it is in the root cgroup.
> For RT systems using `SCHED_DEADLINE`, leave `RT_GROUP_SCHED` **disabled**.

### 12.10 Memory Management — Reduce Latency Sources

**Path:** `General setup` → `Memory Management options`  
or search `/` → `COMPACTION`, `MIGRATION`

```
[*] Allow for memory compaction        CONFIG_COMPACTION
[*] Page migration                     CONFIG_MIGRATION
```

**`COMPACTION`** — background process that defragments physical memory by moving pages.
Can cause latency spikes of hundreds of µs to ms on the CPU running the compaction work.
On a dedicated embedded RT system with no memory pressure, you can disable it:

```
[ ] Allow for memory compaction        # disable if memory is not dynamically allocated
```

**`MIGRATION`** — required for NUMA balancing and compaction. If you disable
`COMPACTION`, you can also disable `MIGRATION`. On RPi4 (single NUMA node, fixed memory),
neither provides benefit and both add latency risk.

**`CONFIG_UNEVICTABLE_LRU`** — keep this enabled; it supports `mlockall()` which your
RT application uses to prevent page faults during execution.

### 12.12 Latency Tracing (Essential for RT Debugging)

**Path:** `Kernel hacking` → `Tracers`

These are the most important options that are **missing from the stock 6.18 RPi
kernel** and must be explicitly enabled in a custom build:

```
[*] Kernel Function Tracer                          CONFIG_FUNCTION_TRACER     (already on)
[*] Interrupts-off Latency Tracer                  CONFIG_IRQSOFF_TRACER      ← enable
[*] Preemption-off Latency Tracer                  CONFIG_PREEMPT_TRACER      ← enable
[*] Scheduling Latency Tracer                      CONFIG_SCHED_TRACER        (already on)
[*] Hardware Latency Tracer                        CONFIG_HWLAT_TRACER        ← enable
[*] OS Noise tracer                                CONFIG_OSNOISE_TRACER      ← enable
[*] Timer Latency tracer                           CONFIG_TIMERLAT_TRACER     ← enable
```

| Tracer | What it measures | How to use |
|---|---|---|
| `IRQSOFF_TRACER` | Maximum time IRQs are disabled | `echo irqsoff > /sys/kernel/tracing/current_tracer` |
| `PREEMPT_TRACER` | Maximum time preemption is disabled | `echo preemptoff > /sys/kernel/tracing/current_tracer` |
| `SCHED_TRACER` | Worst-case wakeup latency (time from wakeup to first execution) | `echo wakeup_rt > /sys/kernel/tracing/current_tracer` |
| `HWLAT_TRACER` | Hardware-induced latency (SMI, firmware stealing CPU) | `echo hwlat > /sys/kernel/tracing/current_tracer` |
| `OSNOISE_TRACER` | Total OS noise on a CPU (IRQs + softirqs + scheduling) | `echo osnoise > /sys/kernel/tracing/current_tracer` |
| `TIMERLAT_TRACER` | Full timer wakeup latency chain breakdown | `echo timerlat > /sys/kernel/tracing/current_tracer` |

**`TIMERLAT_TRACER`** is the most powerful for diagnosing PREEMPT_RT systems — it
measures each stage of a periodic timer wakeup separately:

```bash
# Enable timerlat tracer on CPU 2:
echo timerlat > /sys/kernel/tracing/current_tracer
echo 2 > /sys/kernel/tracing/osnoise/cpus
cat /sys/kernel/tracing/trace

# Output columns:
# IRQ latency | Thd latency | IRQ duration | Thd duration
#    8 µs     |   22 µs     |    3 µs      |    5 µs
#                ^
#     This is where your deadline slack is consumed
```

**`HWLAT_TRACER`** detects SMI (System Management Interrupts) — firmware-level
interrupts that steal CPU time invisibly, often 10–200 µs, completely outside
kernel control. On RPi, HDMI firmware and USB3 firmware can trigger SMIs:

```bash
echo hwlat > /sys/kernel/tracing/current_tracer
echo 1000  > /sys/kernel/tracing/hwlat_detector/width    # sample 1 ms per window
echo 10000 > /sys/kernel/tracing/hwlat_detector/window   # 10 ms window
cat /sys/kernel/tracing/trace    # any output = hardware latency source found
```

### 12.13 Lock Debugging (Development Only — Disable in Production)

**Path:** `Kernel hacking` → `Lock Debugging (spinlocks, mutexes, etc.)`

```
[ ] RT Mutex debugging, deadlock detection     CONFIG_DEBUG_RT_MUTEXES   ← dev only
[ ] Prove locking correctness                  CONFIG_PROVE_LOCKING       ← dev only
[ ] Lock usage statistics                      CONFIG_LOCK_STAT           ← dev only
```

**`PROVE_LOCKING`** (lockdep) — tracks every lock acquisition in the kernel and
detects potential deadlock cycles at runtime. Catches lock ordering bugs that PREEMPT_RT
can expose (since sleeping spinlocks have different nesting rules than spinning ones).
**Adds 10–30% overhead** — use during development, disable in production.

**`DEBUG_RT_MUTEXES`** — validates RT mutex operations and priority inheritance chains.
Use when porting drivers to PREEMPT_RT; disable in final build.

### 12.14 Speculation Mitigations

**Path:** `Processor type and features` → `Mitigations for CPU vulnerabilities`  
or for ARM64: `Kernel Features` → `Mitigations`

```
[ ] Mitigations for speculative execution vulnerabilities     CONFIG_SPECULATION_MITIGATIONS=n
```

Disabling removes Spectre v2 (retpoline), SSBD, and IBRS mitigations.
On RPi4 (Cortex-A72), the measurable overhead is 5–15% CPU for workloads with
frequent syscalls or indirect branches. For an isolated embedded RT system with no
untrusted code execution, this is an acceptable trade-off.

Alternatively, leave the config enabled and use the boot parameter:
`mitigations=off` — gives you the same result without recompiling.

### 12.17 AMP Boot Parameters to Pair with the New Config

Add to `/boot/firmware/cmdline.txt` (single line):

```
isolcpus=domain,managed_irq:2,3 nohz_full=2,3 rcu_nocbs=2,3 threadirqs mitigations=off
```

`domain,managed_irq` requires `CONFIG_CPU_ISOLATION=y` (already in stock RPi config).
`nohz_full=2,3` requires `CONFIG_NO_HZ_FULL=y` (must enable in menuconfig).
`rcu_nocbs=2,3` requires `CONFIG_RCU_NOCB_CPU=y` (must enable in menuconfig).

The combination of `NO_HZ_FULL` + `RCU_NOCB_CPU` + `isolcpus=domain,managed_irq` is
the complete AMP partitioning stack: no scheduler migration, no periodic tick, no RCU
callbacks, and no unaffined IRQs can land on your RT cores.
